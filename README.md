# BEAM SEARCH — The Intelligence Behind Limited Search

*An Interactive AI Search and Decision-Making Explorer* (Streamlit + Plotly)

An interactive laboratory that explains **Beam Search** from fundamentals to advanced ideas.
Every number, tree, path and statistic on screen comes from **really running the algorithm** —
nothing is a hard-coded result.

---

## 1. Run it locally

Requires **Python 3.10+**.

```bash
cd beam_search_explainer

# (recommended) virtual environment
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate

pip install -r requirements.txt
streamlit run app.py
```

Streamlit opens `http://localhost:8501`. Tested on Streamlit 1.40 and the latest release.

Run the tests:

```bash
python -m unittest discover -s tests -v
```

## 2. The eight modules

| # | Module | What you can do |
|---|--------|-----------------|
| 1 | **Understand Beam Search** | Animated walk-through (Play / slider), the rule `B(t+1) = TopK(C(t+1), k)` with every symbol explained, `f(n)=h(n)`, which direction of score is better, concept Q&A, BFS/Greedy/Beam table, applications. |
| 2 | **Search Tree Explorer** | Start / Pause / Resume / Next / Previous / Reset / Run automatically. Node styles for pending, expanding, selected, explored and pruned. Five-question **Decision Explanation Panel** per step, **live statistics**, **pseudocode with the executing line highlighted**, **Learn-by-Prediction mode**, **Experiment mode** (edit any heuristic value), failure demo. |
| 3 | **Beam Width Playground** | Slider `k ∈ {1,2,3,5,10}` re-runs the search. Comparison dashboard over all k (expanded, generated, pruned, retained, time, goal found, path cost vs optimal). Guided experiments: *narrow beam misses the goal* and *wider beam is not optimal*. Random trees with adjustable heuristic noise. |
| 4 | **Maze Solver** | Click cells (or drag a box) to place obstacles / start / goal; random maze, clear, resize; beam width; step-by-step animation; path length, expanded/pruned counts, run time. Honest reporting: *failed but a path exists* vs *goal unreachable* (verified with BFS). |
| 5 | **Text Generation Simulator** | Toy bigram language model (every probability visible), cumulative log-probability scoring, optional length normalisation α, candidate table, hypothesis tree, greedy-vs-beam comparison against the exhaustive optimum. Clearly labelled as **not a real LLM**. |
| 6 | **Algorithm Comparison Lab** | BFS vs Greedy Best-First vs Beam on the same tree or maze: exploration drawn side by side, memory (max nodes held), completeness/optimality table. Takeaways are computed from the runs; the lab never claims Beam always wins. |
| 7 | **Theory & Analysis** | Pseudocode, formulation, complexity with stated assumptions and an interactive calculator **validated against the real algorithm**, completeness and optimality with live counter-examples, pros/cons, applications. |
| 8 | **Quiz Arena** | 15 questions: multiple choice, true/false, predict-the-next-step, identify-the-pruned-node, beam-width experiments, calculations. Many are **generated by running the algorithms on fresh data**. Instant feedback, score, progress, final summary. |
| 9 | **3D Four-Direction Simulator** | Rotatable 3D maze with raised obstacles, four-direction movement, live Beam Search steps, beam-width control, editing and BFS reference. |

**Score direction is always stated:** in the tree and maze demos *lower h(n) is better*
(h = estimated cost to goal); in text generation *higher log-probability is better*.

## 3. How the algorithm is implemented

```
B(0)   = { start }
C(t+1) = ⋃ children(n)  for n in B(t)          # candidates
B(t+1) = TopK(C(t+1), k)                       # keep the k best by h(n); prune the rest
stop when B contains a goal (success) or C is empty (failure)
```

* `algorithms/beam_search.py` — `beam_search()` (explicit trees) and `beam_search_grid()` (mazes).
  With `record=True` it stores a snapshot after each phase (*expand → generate → select/prune → goal test*),
  which is what the UI replays; with `record=False` it is used for timing.
* `top_k()` is a stable sort + slice, so ties are broken by **generation order** (deterministic and
  explained to the user). Beam nodes are expanded in rank order.
* The goal test is applied **after pruning**: a goal must survive selection to be found.
  That is exactly why the algorithm is incomplete, and the lab demonstrates it.
* On grids, every generated cell is *closed* (never generated twice); a pruned cell therefore stays
  discarded for the rest of the run. This is stated in the UI.
* `algorithms/text_generation.py` — beam decoding over a validated toy table `P(next | previous)`,
  cumulative log-probabilities, finished (`<eos>`) hypotheses carried unchanged, optional length
  normalisation `logP / n^α`, plus an exhaustive uniform-cost reference for α = 0.
* `algorithms/bfs.py` and `algorithms/greedy_best_first.py` — baselines with the same result type.
* `algorithms/analysis.py` — closed-form node counts used by Module 7
  (`generated_i = min(b^i, k·b)` etc.), checked against real runs in the tests.

**Complexity (assumptions: uniform branching b, depth d, beam k, O(1) heuristic):**
generated nodes `Σ min(b^i, kb) ≤ d·k·b`; time `O(d·kb·log(kb))` with sorting;
space `O(kb)` candidates + `O(k)` retained (+ `O(kd)` if full paths are stored); BFS is `O(b^d)`.
Beam search is generally **neither complete nor optimal**.

## 5. Sample test cases

Reproduce these in the app (Module 3 / 4) or see them asserted in `tests/`.

| Scenario | k = 1 | k = 2 | k = 3 | k = 5 | k = 10 | What it proves |
|---|---|---|---|---|---|---|
| **Failure demo tree** | ❌ misses goal | ❌ | ❌ | ✅ cost 3 | ✅ cost 3 | A narrow beam can discard the *only* path; the lab names the pruned ancestor. |
| **Cost-trap tree** (optimal = 3) | ✅ cost **3** | ✅ cost 11 | ✅ cost 11 | ✅ 11 | ✅ 11 | A wider beam is **not** automatically better, nor optimal. |
| **Example maze** (shortest = 18) | ❌ trapped | ✅ 36 moves | ✅ **18** | ✅ 18 | ✅ 18 | Fails although a path exists (BFS confirms); k=2 returns a path twice as long. |
| Walled-in goal | ❌ | ❌ | ❌ | ❌ | ❌ | Unreachable goal is reported honestly (BFS confirms no path). |
| Text, prompt *Artificial Intelligence is* | "…is a powerful tool." logP −3.32 | "…is transforming the world." logP **−2.14** | same | same | same | Greedy picks the locally likeliest word and ends up with a less probable sentence. |

Algorithm properties verified by the tests: at most k nodes per beam; selected ⊂ candidates and
disjoint from pruned; every selected node is at least as good as every pruned node; a huge k
behaves like BFS (never prunes); closed-form counts equal measured counts; paths are valid
(adjacent, passable cells); beam never beats the true shortest path; log-probabilities are
true cumulative sums; the toy model's probabilities sum to 1.

## 6. Suggested 5-minute demo for your professor

1. **Module 1** — press *Play*: show the beam narrowing a tree, then the formula and the "lower is better" table.
2. **Module 2** — switch on *Learn by prediction*, step through a level, show the Decision Explanation Panel and the highlighted pseudocode.
3. **Module 3** — click **① Narrow beam misses the goal**, slide k from 1 to 5, point at the dashboard. Then **② Wider beam is not optimal**.
4. **Module 4** — run k = 1 on the example maze (fails, BFS proves a path exists), then k = 3 (shortest path).
5. **Module 5** — compare k = 1 and k = 2 sentences and log-probabilities.
6. **Module 7** — change b, d, k in the complexity calculator and show the "matches the real algorithm" check.

## 7. Troubleshooting

* **Maze clicks do nothing** — clicking needs Streamlit ≥ 1.35. Use *Edit by coordinates* in Module 4 as an alternative.
* **Fonts look different offline** — the theme loads Google Fonts (Nunito, Poppins, Fira Code); without internet it falls back to system fonts.
* **Auto-run seems slow** — lower *Auto-run speed (seconds per step)* in Modules 2, 4 and 5.
* **Port in use** — `streamlit run app.py --server.port 8502`.


## 5. Additive Module 9 — 3D Four-Direction Simulator

The project now includes **9 · 3D Four-Direction Simulator**. This is an additional module; the original eight modules and the original 2D Maze Solver are retained.

- A rotatable, zoomable Plotly 3D maze view with raised obstacle blocks.
- Real execution of the existing `beam_search_grid()` algorithm and the same four-direction movement rules (north, south, east, west).
- Adjustable beam width, random mazes, obstacle editing, start/goal editing, step-by-step replay, and live search statistics.
- BFS is used only as a reference to distinguish a Beam Search pruning failure from a genuinely unreachable goal.

The 3D height is a visualization layer for the maze cells and obstacle blocks; the search itself remains four-directional on the grid plane. This keeps the simulation consistent with the Manhattan heuristic and the original algorithm implementation.
